# Status — the review skills, 26 August 2026

Where `write-critical-guide` and `write-paper-repairs` stand, what is validated against real
work and what is only designed, and what is open. Written because this is the part that
evaporates between sessions: the designs are documented, their *status* is not.

## What exists

| skill | produces | state |
|---|---|---|
| `write-critical-guide` | working material for assessing and evaluating one paper — summary, graded issue list, repairs, annotated sources | **validated** on two real papers |
| `write-paper-repairs` | repairs written into the paper's own source as tracked changes; proposals shown in position; a critical report | mechanism **validated**, scoping thin |

Shared: `skills/write-critical-guide/tools/annotate_tex.py` generates the issue list and the
annotated sources from one ledger; `skills/write-paper-repairs/assets/agentic-edits.tex` carries
the three-state tracked-change markup.

## Validated, and against what

**`write-critical-guide`** — two complete packages exist, both hand-checked:

- `reviewing/clifford/` — Journal of Algebra second revision, 29 pp. 235 issues (9 major
  mathematical). Its `review-notes/refuted-and-dropped.md` records the case that justifies the
  adversarial phase: a charge of uncited duplication, refuted by two skeptics on five
  independent grounds, which would have put a false accusation of misconduct to the authors.
- `reviewing/colton/` — 274 issues, and it **invented a fourth category** (`attribution`) on its
  own, which the loosened category rules were written to allow. Its literature audit found 10 of
  12 claims needed weakening.

**`write-paper-repairs`** — one trial, six issues on clifford. Seventeen skeptics; four of six
left the audit in a different state; two errors found in the guide's own ledger. Markup verified
against `amsart` and `elsarticle` including in-display changes, counter freezing, and label
suppression.

## Designed but not validated

**Chunked review of long documents** (`write-critical-guide/references/long-documents.md`). The
whole design is `review-state.yaml`, the carry file between sessions. Nothing has been run
through it.

The field to watch first is **`inherited`** — it asks a chunk-3 agent to notice that what it is
grading rests on an open chunk-1 defect. It is the least mechanical field and the one the design
rests on. If it fails it will fail quietly.

**Scoping and triage in `write-paper-repairs`** (Phases 1–2) rest on one run of six hand-picked
issues. That is not the same problem as deciding what to do with 274.

## Open threads

- **Colton's repair run was never done.** Its shape differs from clifford's: 31 of 55 major
  mathematical issues are *absences* (no proof given, never defined) rather than positive
  errors, and absences are not repairable — supplying a missing proof is doing the authors'
  work. Plan: triage first, repair 8–10 dependency roots among the 24 positive errors,
  consolidate the absences into a statement rather than enumerating them.
- **`annotate_tex.py` annotates one file.** Fine for papers and for chunked books, where each
  chunk's source is its own chapter file. A genuinely monolithic long document still needs the
  `structure[].lines` range the schema reserves.
- **Both an installed plugin and `~/.claude/skills/` symlinks exist**, so which copy a run used
  is not determinable. See below.

## Installation, and the ambiguity in it

All ten skills resolve their own plugin root (try `${CLAUDE_PLUGIN_ROOT}`, else resolve the
skill's base directory and take its grandparent), so **both install modes work**. Both are
currently present, which is the problem: eight skills are symlinked *and* all ten are in the
version-keyed plugin cache, and nothing says which one a given run read.

They behave differently. The plugin cache is a **copy**, keyed by version: edits to the checkout
do not appear until `version` in `plugin.json` is bumped and `claude plugin update` run. That
divergence has already happened once in practice — a rule was committed to the repo and was not
in the running skill.

Recommendation on file: keep symlinks on the authoring machine, install the plugin elsewhere.
Provenance for a questionable run comes from `git log` on the skill file, which is better than a
version number anyway.
